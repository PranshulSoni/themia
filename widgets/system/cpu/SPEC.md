# CPU Monitor: Spec

Behavior tags are stable IDs. When adding behavior, append a new [S-NN]; never renumber or reuse existing tags. When behavior is removed, delete the bullet but don't reuse its tag.

## Display
- [S-01] Header row shows the configured `label` (defaulting to "CPU"), current CPU usage percent to one decimal, and CPU frequency in GHz to two decimals when available.
- [S-02] Header is hidden when `hideHeader` is true.
- [S-03] When `showGraph` is true and per-core view is disabled, renders an aggregate usage sparkline (area + line) scaled 0–100%.
- [S-04] Sparkline retains the most recent 40 samples.
- [S-05] A horizontal bar track shows the current CPU usage fill proportional to percent.
- [S-06] Usage color is cyan (`--primary`) below 70%, amber (`#f59e0b`) at 70–89%, red (`--destructive`) at 90%+; applied to the percent text, sparkline stroke/gradient, and bar fill.
- [S-07] When `showCores` is true and core data is available, replaces the aggregate graph with a per-core grid; each cell shows core index, a per-core sparkline, and the core's current usage percent using the same color thresholds.

## Configuration
- [S-08] `showCores` toggle (Display tab) switches between aggregate and per-core view.
- [S-09] `showGraph` toggle (Display tab) shows/hides the aggregate sparkline; defaults to on.
- [S-10] `hideHeader` toggle (config Header field, shared by all widgets) shows/hides the header row.
- [S-11] `interval` segmented control (Refresh tab) selects polling period from {1, 2, 5, 10, 30} seconds; defaults to 2s.

## Data / backend
- [S-12] Polls Tauri command `get_system_stats` every `max(1, interval)` seconds via `createPolling` with key "cpu".
- [S-13] Backend exposes `cpu_usage` (global %), `cpu_cores` (per-core %), and `cpu_freq_mhz` sampled from `sysinfo`. The per-tick refresh uses `CpuRefreshKind::new().with_cpu_usage().with_frequency()`: `refresh_cpu_usage()` alone leaves `Cpu::frequency()` at 0, which the frontend treats as unavailable and hides the GHz row (issue #40 regression: `cpu_freq_mhz` must be nonzero on real hardware).
- [S-14] Backend debounces `get_system_stats` with a 500 ms shared cache so multiple system widgets share one refresh. A cached sample built without process metrics is not served to a caller that requests them ([S-21]); a sample built with them is served to everyone.
- [S-21] `get_system_stats` takes `includeProcs` / `includeTemp` flags. The widget passes `includeProcs: true` only when `topProcs` or `processes` is visible, and `includeTemp: true` when `temperature` **or** `fan` is visible (the WMI sensor sampler reads temperature and fan RPM together, see [S-23]). With `includeProcs: false` the backend skips the full process-table refresh entirely and returns empty `cpu_top`/`ram_top` and zero `cpu_processes_total`/`cpu_threads_total`.
- [S-22] `get_system_stats` is an async command executed via `spawn_blocking`, so sampling (process fan-out, PDH, per-volume free-space queries) never runs on the main event-loop thread.

## Per-metric visibility
- [S-15] `visibleMetrics` config (string[]) selects which metric rows render. Defaults to `['usage','frequency','graph']`. Legacy `showGraph`/`showCores` props honoured when `visibleMetrics` is absent.
- [S-16] Available metrics: `usage`, `frequency`, `graph`, `cores`, `temperature`, `fan`, `topProcs`, `processes`, `uptime`.
- [S-17] `topProcs` shows the `topProcsCount` ([S-26]) highest CPU processes (name + percent), sourced from backend `cpu_top` sorted desc. Per-process CPU is derived from cumulative kernel+user time deltas ([S-24]).
- [S-18] `processes` shows total process count (and thread count when available) from backend `cpu_processes_total`/`cpu_threads_total`. On Windows the thread count is the real sum of every process's `NumberOfThreads` ([S-24]); the idle process (PID 0) is excluded from both counts.
- [S-24] On Windows the process table (top CPU, top memory, process/thread counts) is enumerated via `NtQuerySystemInformation(SystemProcessInformation)`, **not** sysinfo's handle-based per-process reads. sysinfo derives per-process CPU/memory from `GetProcessTimes`/working-set queries that need an `OpenProcess` handle; that handle fails for protected/elevated/system processes when Themia runs unelevated (Windows Update's TiWorker/TrustedInstaller, Defender's MsMpEng, Hyper-V's vmmem/vmwp, …), so they read back as 0% and never surfaced in the top lists (themia-releases#50). `NtQuerySystemInformation` returns kernel+user times and working set for every PID with no per-process handle, the same source Task Manager uses. Per-process CPU% is the cumulative-time delta between consecutive samples over the elapsed window, on sysinfo's single-core scale (a process pegging one core = 100%), then normalised by core count for display. The idle process (PID 0) is excluded (its "busy" time is the machine idling); a PID seen for the first time (or on the first sample) reports 0% until the next tick. Non-Windows targets keep sysinfo's process table.
- [S-19] `uptime` shows system uptime formatted as `Nd Nh`, `Nh Nm`, or `Nm` (largest two units).
- [S-20] `temperature` reads `cpu_temp_c` from backend. Two WMI sources are tried, in order, on one dedicated worker thread (its own MTA COM library, since COM init on the STA main thread fails with RPC_E_CHANGED_MODE), started lazily on the first poll with `includeTemp: true` ([S-21]):
  1. The **LibreHardwareMonitor** (`root\LibreHardwareMonitor`, falling back to the older **OpenHardwareMonitor** `root\OpenHardwareMonitor`) `Sensor` class. Among `SensorType = "Temperature"` rows whose name mentions the CPU (`cpu`/`tctl`/`tdie`/`core`), a package/Tctl/Tdie reading is preferred over the hottest per-core; readings outside 0–150 °C are rejected. This source covers modern consumer AMD/Ryzen boards whose on-die Tctl/Tdie sensor is exposed only over the SMU/SMN (issue #36) **without Themia bundling a kernel driver**: LHM ships its own signed driver. It is opt-in: the user installs/runs LHM (or OHM).
  2. **ACPI thermal zone** (`MSAcpi_ThermalZoneTemperature`, `root\wmi`, tenths-of-Kelvin → °C of the hottest zone), used when LHM/OHM is not running or exposes no CPU temperature. Commonly absent on consumer AMD boards.

  The sampler publishes the latest reading; it samples every 5 s while any sensor reports, backing off to 60 s otherwise. Issue #60: unlike its earlier behavior (row hidden entirely when no source yielded a value), an **enabled** `temperature` metric is never silently hidden once stats load — the same fix the fan metric got in #40 ([S-23]). The chip shows the °C reading when a source yields one, otherwise a **"Temp N/A"** placeholder (subtle-foreground, tooltip explaining LHM/OHM is required). The display decision is the pure `tempCell` helper (`tempDisplay.ts`), which returns null before the first poll to avoid an "N/A" flash. Previously the chip was gated on a non-null reading, so on the common case of no sensor the toggled-on metric vanished and read as broken.
- [S-25] Each `topProcs` row shows the process's "real" (friendly) name — the exe's version-info **FileDescription**, the same string Task Manager's process list shows (e.g. "Google Chrome" for chrome.exe) — with the image name in the row tooltip. The backend resolves it per surfaced row via `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)` → `QueryFullProcessImageNameW` → `GetFileVersionInfoW`/`VerQueryValueW` (translation-table languages first, en-US/Unicode block as fallback), cached per exe path (cleared past 512 entries). Protected/elevated processes refuse even a limited handle when Themia runs unelevated and exes may lack a version resource; those rows get `desc: null` and the frontend falls back to the image name. Blank descriptions count as absent. Non-Windows targets always send `desc: null`.
- [S-26] `topProcsCount` config (Display tab, visible only while `topProcs` is enabled) selects how many process rows render: 1–10, default 3. The value is clamped and non-numeric persisted junk falls back to the default (`clampProcCount`). The backend always returns up to 10 rows (`CPU_TOP_N`) so the frontend slice never starves; the count is a display concern only and does not change the IPC args ([S-21]).
- [S-23] `fan` reads `cpu_fan_rpm` from backend: the highest plausible (1–60000) `SensorType = "Fan"` reading whose name mentions the CPU, from the same LibreHardwareMonitor/OpenHardwareMonitor source as [S-20] (one sampler reads temp + fan together). There is no no-driver fan source without LHM/OHM, so the value is null unless LHM/OHM exposes a CPU fan. Unlike `temperature` (which hides when its two sources are both absent), an **enabled** `fan` metric is never silently hidden once stats load: the chip shows "N RPM" when a sensor is present, otherwise an **"Fan N/A"** placeholder (subtle-foreground, tooltip explaining LHM/OHM is required). The display decision is the pure `fanCell` helper (`fanDisplay.ts`), which returns null before the first poll to avoid an "N/A" flash. Issue #40: previously the fan chip was gated on a non-null reading, so on the common case of LHM/OHM not running the toggled-on metric vanished and read as broken.
