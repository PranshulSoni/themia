# To Do Spec

Behavior tags are stable IDs. When adding behavior, append a new [S-NN]; never renumber or reuse existing tags. When behavior is removed, delete the bullet but don't reuse its tag.

## Display
- [S-01] Shows tasks from the selected task list on the chosen Microsoft or Google account.
- [S-02] Header shows a check-square icon, the list name (or custom `label`), and an active-task count badge; hidden when `hideHeader` true. The name of a device list comes from the pool ([S-57]), so renaming it in the config retitles the widget live. The badge is gated on the RENDER state, not the fetch state machine, which never leaves "loading" in local mode — that is why the count used to be an account-mode-only feature.
- [S-03] Empty state prompts "Select account" when no account configured.
- [S-04] "Select task list" state shown when an account is selected but no list.
- [S-05] "Re-sign in to grant To Do permissions" state shown on `todo_not_authorized` error.
- [S-06] Error state shows the raw error string for other failures, except the `network_error` sentinel, which is localized ([S-63]).
- [S-07] Loading state shown as a spinning refresh icon while initial fetch pending.
- [S-08] Each task row shows a circle (incomplete) or check-circle (completed) button, the task title, and the formatted due date.
- [S-09] Due-date label: "overdue" / "today" / "tomorrow" / short weekday / "Mon Day", derived from the resolved due day ([S-48]) and the local day count (rounded, so a DST boundary between them doesn't shift it).
- [S-10] Past-due dates for incomplete tasks are highlighted as overdue.
- [S-48] A due date is a calendar *day*, but both backends ship it as a datetime, in either of two encodings: midnight of the intended day (Graph zoneless, Graph/Google UTC `Z`, or a bare date), or the creator's local midnight already converted to UTC (the Microsoft To Do mobile app, e.g. `...T17:00:00` the day before for a UTC+7 user). `dueDay` reads the first kind's date part verbatim — converting it through UTC would push viewers at a negative offset (the Americas) back a day — and resolves the second by parsing zone-aware (zoneless means UTC, as in calendar `gdt`, issue #48) and taking the viewer's local day. Regression tests `S-48_` (issue nwalser/themia-releases#101: tasks due today showed "overdue", tasks due Monday showed Sunday).
- [S-11] High-importance tasks show a "!" badge.
- [S-12] Completed tasks render with the "done" visual state.
- [S-13] Bottom fade overlay appears when the list can scroll further down.
- [S-49] A task title that doesn't fit WRAPS. It wraps to `titleLines` lines (`--todo-title-lines`, a `-webkit-box` clamp) and only then cuts off with an ellipsis, with the full text on the row's native tooltip and the unclamped editor ([S-50]) one click away. `titleLines` is user-set (config > Display, 1–`TITLE_LINES_MAX`, default `TITLE_LINES_DEFAULT`) because how much vertical room a task may take is a density choice, not something the widget can guess. It is an untrusted config value, narrowed through `clampTitleLines`: non-numeric → default, out of range → clamped, fractional → floored, so no config can produce a zero-height or unbounded row. `overflow-wrap: anywhere` keeps one unbroken token (a URL, a path) inside the row instead of widening the list. Requested on issue nwalser/themia-releases#104. Two earlier answers were rejected: a self-scrolling marquee (an always-on-desktop widget must not move on its own) and drag-to-pan on a single nowrap line (it put a grab cursor on every long task and still only showed one line at a time). Tests: `titleLines.test.ts` (`clampTitleLines [S-49]`).
- [S-14] "Add task" row at the bottom becomes an inline input when clicked.

## Local storage mode
- [S-41] `storageMode`: `account` (Microsoft/Google, the default) or `local`. In `local` mode the tasks come from the DEVICE-WIDE list pool ([S-57]) rather than any account: the widget's config holds only `localListId`, the id of the list it shows. Pure state: no account, fetch, IPC, or polling.
- [S-42] Local tasks are read from the untrusted stored value through `parseLocalTasks` at the trust boundary: a non-array (absent/corrupt) yields an empty list; entries missing a string `id`/`title` are dropped (siblings kept); a non-boolean `done` defaults to false. Stored task shape is lean `{ id, title, done }` (no importance/due-date/list metadata, which a local task has no source for).
- [S-57] "This device" owns MANY NAMED LISTS, the same way an account does, and each widget points at one. They live in a device-wide store (`localListStore.ts`, persisted bare under `todo-local-lists`, schema-validated through `parseLocalLists`, written via `sharedStorage` so every window is notified reliably) — NOT in a widget's config bag, because a pool you select from and create into has to outlive the widget that made it and be reachable from the config window, the grid tile and a pop-out at once. Consequences: renaming a list retitles every widget showing it, live; deleting a widget no longer destroys its tasks; two widgets may show the same list; and the list — not the widget — is what an export has to carry (`importExport`'s `todoLocalLists`, written on import only when the file has it, since a pre-pool export cannot express "no lists"). `parseLocalLists` drops an entry without a non-empty string `id` or a string `name`, and drops a REPEATED id keeping the first — every lookup and write here is by id, so a duplicate would make "which list is this" ambiguous. Tests: `localLists.test.ts` (`S-57_`).
- [S-58] The config panel is where lists are picked, created, renamed and deleted, inside the "This device" source card ([S-61]) and only in local mode. A row is: the pick DOT (the widget's own circle/check-circle, the one control that changes state), the name as an always-editable input writing through on each keystroke, the task count, and a remove button; a `btn-add` under the list creates one, named uniquely (`New list`, `New list 2`, …) and selected immediately. Deleting a list that HAS tasks confirms through the native dialog first (unrecoverable); the widgets showing it fall back to the "pick or create a list" empty state rather than being silently handed another list's tasks — which is also what a widget whose `localListId` names a missing list shows. Blank names are kept while typing (unlike a task title, [S-50]) because refusing the empty string makes the field impossible to clear before retyping. Built from the shared collection-editor primitives (`items-list` / `item-remove` / `btn-add`, Settings.SPEC [S-11]/[S-18]).
- [S-59] The pre-pool `localTasks` config bag migrates ONCE into a real list, on mount. The new list's id is DERIVED from the widget id (`list-migrated-<widgetId>`), so a grid tile and a pop-out of the same widget — which mount together and both see the bag — converge on one list instead of seeding two, and `seedLocalList` leaves an existing id alone rather than overwriting tasks. The same config write that points at the new list clears the bag, so the tasks exist in exactly one place afterwards and the migration cannot run twice. Two widgets that each had their own tasks become two lists, named from the widget's label (or "My tasks", uniquified).
- [S-43] Local "Add task" APPENDS a new active task at the bottom ([S-55]), trimming the title; a blank/whitespace title is a no-op.
- [S-44] Toggling a local task (click, Enter, or the row menu) flips its `done` flag and writes the array back to config.
- [S-45] Deleting a local task (row menu or Delete key) removes it from config.
- [S-46] `showCompleted` hides completed local tasks from the display while keeping them in storage (event-driven; completing a task with completed hidden makes it disappear reactively, no timed removal).
- [S-47] Local mode does no account fetch or polling. The config panel offers "This device" as the FIRST row of the account list (`AccountToggleList` `leadingEntry`), styled like an account row with its own toggle, and selected the same single-select way: enabling it clears any account + list; picking an account disables it. Enabling it also lands the widget on a usable list ([S-57]): the one it had before if that still exists, else the first list on the device, else a newly created one — only the last case creates anything, so toggling the source back and forth cannot litter the pool with empty lists. Each source shows its own list picker in its own card ([S-61]), and the Refresh (interval) section is dropped from the tab list in local mode.

## Today (virtual list)
- [S-52] "Today" is a cross-list view, offered as the FIRST entry of the task-list picker (badge "all lists") above the account's real lists, and stored as the reserved `listId` `__today__` (`todayList.ts` / Rust `TODAY_LIST_ID`, kept in sync). It holds every task **due today or overdue**, across every list on the account, oldest first; a task with no due date is not in it. Its header name comes from the current language, not the `listName` frozen at pick time. Adding a task from Today creates it **due today** in the account's *default* list (the frontend sends a bare `YYYY-MM-DD` `dueDate`; `valid_due_day` rejects any other shape), so it doesn't vanish from the view it was typed into; the optimistic row carries the same day. Because the rows come from many lists, every write (`todo_update_task` / `todo_rename_task` / `todo_delete_task`) is addressed to **the task's own `list_id`**, not the selected one. Backend: `todo_get_tasks` with `__today__` reads the lists, then fans out over them (capped at `TODAY_MAX_LISTS` = 50); a single list that fails is skipped and logged, but if every list fails the error is surfaced rather than an empty "nothing due". The day filter itself stays on the frontend, next to the day resolution it depends on ([S-48]) — Rust returns all lists' tasks unfiltered. Tests: `todayList.test.ts` (`S-52_`), Rust `graph_todo_today_fans_out_across_lists`, `todo_today_skips_a_failing_list`, `todo_today_surfaces_error_when_every_list_fails`.
  - This is NOT Microsoft To Do's own "My Day", which no API exposes: Graph has no My Day property on `todoTask` (v1.0 or beta), `wellknownListName` is only `none | defaultList | flaggedEmails`, and `/beta/me/planner/myDayTasks` returns *Planner* tasks and is work-or-school only. Today implements the half of Microsoft's own definition of that view ("added to it, or due today") that is visible over the API, and is named "Today" rather than "My Day" so it doesn't promise the manual-add sync it can't deliver. Requested on issue nwalser/themia-releases#80.

## Throttling and network failure
- [S-63] A throttled or unreachable backend is something the widget RIDES OUT, not something it reports. Three parts, all provoked by Today ([S-52]), which turns one poll into one request per list:
  - **Backoff.** Every To Do read (Graph and Google, lists and tasks, each page) goes through `get_with_retry`: a 429/503 is retried up to 3 times honoring the server's `Retry-After`, clamped to 30s, falling back to 1s/2s/4s when the header is absent. To Do was the last Graph caller in the app still making a single attempt, so the burst the whole dashboard makes on load — calendar, email and contacts all back off — landed on To Do as a hard "Graph API error 429" that only a manual reload cleared. A throttle that never clears still gives up and surfaces the status.
  - **No stacked polls.** A poll tick is SKIPPED while a fetch is still out. `createPolling` is a plain `setInterval` and does not wait for `load()`, so a fan-out that outlasts the interval used to have the next tick fire another full round of requests at the server already rate-limiting us — the throttle fed itself. The request-id guard ([S-40]) only discards the stale *result*; the request had already gone out. A selection change still loads immediately (it is not a tick).
  - **A cause, in the user's language.** A transport failure (DNS, TLS, reset, timeout) returns the `network_error` sentinel, which the widget and the config panel render as `todo.networkError`. `reqwest`'s own text — "error sending request for url (https://graph.microsoft.com/v1.0/me/todo/lists)" — names the URL but not the cause, and reached the user untranslated; the full `source` chain now goes to the log instead. Issue nwalser/themia-releases#113. Tests: Rust `s63_*`.

## Config panel
- [S-61] The list picker lives INSIDE ITS SOURCE'S CARD, not as a row beside the source list: each source renders its own picker in the `AccountToggleList` slot under its row (`perAccountExtra` for an account, `extra` for the "This device" leading option), indented like the calendar widget's per-account calendar list and the notes widget's note picker. A list is provider-specific — the device's lists are a pool this panel creates, renames and deletes ([S-58]); an account's are read back from Microsoft or Google and only selected ([S-16]); Today is a client-side view over one account's lists ([S-52]) and so belongs to that account's card too. As one row below the whole source list, the picker read as a global setting and had to be gated on `storageMode` + "is an account selected" to say which source it meant; under the row it says so by position, and a second selected source would get its own picker rather than fighting for the one slot. Only the SELECTED account draws a picker (an unselected account has no lists to choose from), and only in account mode.
- [S-53] The task-list fetch reacts to the **selected account**, not the config bag it lives in. The panel is stateless by rule ([S-13]) and `update()` writes a whole new config object, so an effect that reads the config to find the account re-ran — and refetched — on every unrelated write (picking a list, view mode, title lines, show-completed), flipping the picker back to its loading line each time and making the panel jump on every click. `createTaskLists` (`taskLists.ts`) memoises the account id, so a new config object carrying the same account is not a change; `revision` (accounts added/removed elsewhere) still forces a refetch, and a request-id guard keeps a superseded in-flight fetch — including one outrun by `reset()` — from landing on the current lists. The loading line only ever stands in for the picker when there are no lists to draw (`pending`): a refresh keeps the existing rows on screen. `reset()` is for switches that invalidate the lists outright (different account, going local). Tests: `taskLists.test.ts` (`S-53_`).

## Configuration
- [S-15] `accountIds`: single selected Microsoft or Google account.
- [S-60] `localListId`: which device list this widget shows in local mode ([S-57]). The tasks are NOT config; this is a pointer into the shared pool.
- [S-62] Deleting a device list always confirms through the native dialog, empty or not — it takes every task in it, and the X sits one row from the name field the user was just typing in. An empty list gets the shared noun-free body (`common.deleteEmptyConfirm`), because "and its 0 tasks" is not a sentence.
- [S-16] `listId` / `listName`: selected task list from `todo_get_lists`, or the virtual Today id ([S-52]); default list auto-selected when the account changes.
- [S-17] `viewMode`: `list` | `compact` (compact shows the due date inline instead of under the title).
- [S-51] `titleLines`: how many wrapped lines of a task title to show before clamping ([S-49]).
- [S-18] `showCompleted`: include tasks already completed.
- [S-19] `refreshInterval`: 30s / 1m / 5m / 10m polling cadence.
- [S-20] `hideHeader`: toggle the widget title bar.

## Context menu
- [S-21] Widget chrome right-click offers Refresh, view-mode switcher (List/Compact), and Show/Hide completed toggle.
- [S-22] Task right-click offers Mark complete/incomplete (toggles based on current state) and Delete.
- [S-39] To Do opts into the generic widget pop-out (registry `popOut`): the "Open in window" chrome action opens the list in its own decorated OS window via `open_widget_window`; the window renders the same widget bound to the shared per-view layout store (see src/WidgetWindow).

## Data / backend
- [S-23] Tasks fetched via `todo_get_tasks` with account id, list id, and show-completed flag.
- [S-24] Lists fetched via `todo_get_lists` in the config panel; re-runs when accounts change via `accountRevision`.
- [S-25] Toggle status invokes `todo_update_task`; reverts on failure.
- [S-26] When completing a task with `showCompleted` off, the task is removed from the list after a brief delay.
- [S-27] Delete invokes `todo_delete_task`; restores the task at its original index if the call fails.
- [S-28] Create invokes `todo_create_task`; shown optimistically with a temporary id and replaced by the server task on success.
- [S-29] Polls at the configured `refreshInterval`.
- [S-30] Reloads when the account, list id, `showCompleted`, or `_refresh` token changes.
- [S-40] `load()` guards overlapping fetches with a request id: a slower in-flight poll for a previously-selected list is discarded rather than overwriting the tasks of the newly-selected list (#31).

## Interactions
- [S-31] Completing a task is the circle/check-circle DOT's job and nothing else's: it is a real `<button>` whose click toggles the status (and focuses the row), and it stops propagation so the row doesn't also handle it. Clicking anywhere else on the row only moves the keyboard focus. The row used to be one big toggle, which meant every click to read, focus or rename a task also ticked it off (issue nwalser/themia-releases#104). The row therefore no longer takes `cursor: pointer` — the dot and the title carry their own cursors.
- [S-50] A task is renamed in place, from the widget. Clicking the title, pressing F2 on the keyboard-focused row, or the row menu's Rename opens an inline editor seeded with the current title; Enter or blur commits, Escape cancels. The caret lands WHERE THE CLICK DID (`caretOffsetFromPoint` → `focusWithCaret`, `src/input/caret.ts`) and NOTHING is selected: opening with the whole title selected armed the next keystroke to wipe it, which is not what clicking into text means anywhere else. The keyboard routes carry no click point and park the caret at the end — still not a select-all. Tests: `caret.test.ts`. The editor is a `<textarea>` grown to its content (`growToFit`), so the WHOLE title is visible while editing however few lines the display clamps to — but Enter still commits rather than inserting a newline, since a task title is one line of text to both backends. A blank or unchanged title commits nothing — deleting is the row menu's job, and a task with no title can't be recovered from the UI. Local mode writes through `renameLocalTask`; account mode updates optimistically and reverts on failure, via `todo_rename_task` (a PATCH carrying only `title`, kept separate from `todo_update_task` so neither call can clear the other's field). Only the id of the row being edited is tracked, so a poll that swaps the task list mid-edit can't strand the editor on a stale row. Tests: `localTasks.test.ts` (`renameLocalTask [S-50]`).
- [S-32] "Add task" row opens the inline editor, which auto-focuses; Enter creates the task; Escape or empty blur cancels; blur with text commits. The editor is a `<textarea>` grown to its content (`growToFit`), the same as the rename editor ([S-50]), so a long task WRAPS as it is typed instead of scrolling sideways out of view — Enter still commits rather than inserting a newline.
- [S-33] Arrow Up/Down move keyboard focus; Home/End jump to first/last; Escape clears focus.
- [S-54] Tasks are REORDERED BY DRAGGING a row. Neither backend can store the order — Graph's `todoTask` exposes no ordering property at all and Google Tasks' move endpoint is its own list's — so the arrangement lives in the widget: in **account** mode as a `taskOrder` array of task ids in config (narrowed from the untrusted value by `parseTaskOrder`), and in **local** mode as the stored `localTasks` array itself, which IS the order (one storage per mode, never both). `applyTaskOrder` puts the ids the order names first and everything else after, so a deleted id leaves no hole, a corrupt duplicate can't double a row, and an unknown id — a task that was just created — lands at the bottom ([S-55]). An EMPTY order returns the backend's rows untouched, so an untouched widget keeps the server's own sorting (including Today's oldest-first, [S-52]). A local reorder rewrites only the slots of the tasks that were visible: a completed task hidden by [S-46] keeps its absolute position rather than being resurrected or shuffled. The gesture is the same OS-cursor POLLING one the folder, shortcut and habit widgets use (`get_cursor_state` at ~60 fps, `gesture.ts`'s 5px threshold), because a widget window is `WS_EX_NOACTIVATE` — Chromium withholds mousemove while a button is held — and Rust owns its OLE drop target, so `dragover` never reaches the DOM either. It reorders a LOCAL copy and commits once on release (`sameOrder` → a drag that comes home writes nothing). A press on the dot or inside the editor arms nothing, and a drag that ends on a title does not also open the rename. Mouse states: the row is `grab`, the list turns `grabbing` while a drag is live, and the dragged row fades. Tests: `taskOrder.test.ts`, `localTasks.test.ts` (`reorderLocalTasks [S-54]`).
- [S-55] A newly created task appears at the BOTTOM, where it was typed. Local mode appends ([S-43]); account mode inserts the optimistic row last and then PINS the arrangement on screen into `taskOrder` once the server task arrives, because the next poll would otherwise re-impose the backend's own sorting — Graph returns its lists most-recently-changed first, which is how a just-added task kept jumping to the top. The pinned order is rebuilt from the rendered rows, so ids of deleted tasks prune themselves instead of accumulating. Tests: `taskOrder.test.ts` (`applyTaskOrder … BOTTOM [S-55]`), `localTasks.test.ts` (`APPENDS … [S-55]`).
- [S-56] TAB navigation. With no editor open, Tab moves the keyboard focus to the next row and Shift+Tab to the previous, WRAPPING at both ends (unlike the arrows, which clamp — Tab is a "next one" key, not a directional one). While a row's editor is open, Tab commits it and opens the NEXT row's editor (Shift+Tab the previous), so a list can be corrected end to end without the mouse; past either end the editor simply closes rather than wrapping the caret somewhere the user isn't looking. In the "Add task" editor, Tab commits and leaves the row open for the next task, and Shift+Tab commits and closes it. Tab reaches the widget through the Rust hook's whitelist (`widget_kb_action`, VK 0x09) when no text input is focused, and as a plain DOM keydown when one is ([S-38]). Test: Rust `n35_widget_kb_action_classification`.
- [S-34] Enter on the focused task toggles its completed state.
- [S-35] Delete key deletes the focused task and moves focus to the neighbor.
- [S-37] The keyboard-focus highlight resets when the user clicks anywhere outside a task row (the widget's own chrome, another widget) via a global mousedown handler, and when the Themia app loses focus entirely (clicking another app or the desktop) via the shared `onAppBlur` helper (Rust `themia-blur` broadcast + `window blur` fallback). Mirrors the folder / shortcut / contacts / email widgets.
- [S-36] Keyboard input routed via the Rust low-level hook; mousedown activates the widget's keyboard router.
- [S-38] While the inline add-task input (or any text input) is focused, the Rust keyboard hook stands down (`set_text_input_focused` bridge): Backspace/Enter/Escape/arrows/Ctrl+A act on the input natively, and Backspaces injected by IME tools (e.g. Vietnamese Telex, such as Unikey/EVKey) are not swallowed, so composed characters replace correctly. The app-level shortcut block stands down too: Ctrl+Z falls through to the input's native text undo (not the file-operation undo broadcast) and Ctrl+1-9 do not switch views (a switch unmounts the widget tree and discards the in-progress edit). Exception: Ctrl+E/W stay consumed by the hook, since passing them through hands them to WebView2's browser accelerators (Ctrl+W = close window); the JS hotkey dispatcher ignores them while an input is focused, so consuming is a safe no-op. Regression tests: Rust `n35_*` (issue nwalser/themia-releases#35), `s38_*` (app-level keys).
