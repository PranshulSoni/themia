# Email Spec

Behavior tags are stable IDs. When adding behavior, append a new [S-NN]; never renumber or reuse existing tags. When behavior is removed, delete the bullet but don't reuse its tag.

## Display
- [S-01] Shows messages from configured Microsoft, Google, and/or IMAP accounts for the selected folder.
- [S-02] Header shows a mail icon, the folder label (Inbox / Sent / Drafts / Deleted / Junk, or custom `label`), an unread-count badge, and a sort-order toggle button.
- [S-03] Header is hidden when `hideHeader` is true.
- [S-04] Empty state prompts the user to select an account when no account is configured.
- [S-05] Shows a "Loading…" state while the initial fetch is in flight.
- [S-06] Shows an error state when the backend fetch fails.
- [S-07] Unread messages render with bold sender/subject and a closed-envelope icon; read messages use an open-envelope icon.
- [S-08] When messages come from multiple accounts, each row shows an account tag with nickname/email and a provider label.
- [S-09] Relative time (just now / Nm / Nh / Nd / Mon Day) for list/compact; row view uses a fuller time/weekday/date format.
- [S-10] Bottom scroll-fade overlay appears when the list has more content below the viewport.

## Configuration
- [S-11] `accountIds`: multi-select list of Microsoft/Google/IMAP accounts to merge into the feed.
- [S-12] `folder`: `inbox` | `sentitems` | `drafts` | `deleteditems` | `junkemail` selected via dropdown.
- [S-13] `messageCount`: max messages to load (1–50).
- [S-14] `viewMode`: `list` | `compact` | `row`.
- [S-15] `previewLines`: visible body-preview lines per message in list view (1–5).
- [S-16] `rowColumns`: which columns (From, Subject, Date, Preview, Account) appear in row view; at least one must remain selected.
- [S-43] `listFields`: which optional fields (Subject, Preview, Account) appear in list & compact view; From and time are always shown. Preview only renders in list view. The account tag shows whenever the user has enabled the Account field, regardless of how many accounts the feed spans (issue #45c: the account tag no longer requires a multi-account feed — it now mirrors Row view, where the Account column shows whenever selected). Defaults to all three on (preserving prior behavior). Preview-lines control is shown only when `viewMode` is `list` and Preview is selected.
- [S-17] `sortOrder`: `desc` (newest first) or `asc` (oldest first).
- [S-18] *(removed)* Per-widget item spacing is no longer configurable; the list gap is fixed by row padding.
- [S-19] `hideHeader`: toggle the widget title bar.

## Context menu
- [S-20] Widget chrome right-click offers Refresh, view-mode switcher (List/Compact/Row), folder picker (Inbox/Sent/Drafts/Deleted/Junk), and sort order (Newest/Oldest first).
- [S-21] Message right-click offers Open, Reply, Mark read/unread (toggles based on current state), Archive, Junk (move to junk), Copy subject, Delete.
- [S-22] For Google messages (gmail.readonly scope), Mark read/unread, Archive, Junk, and Delete are hidden.
- [S-23] Header sort button in the title bar toggles between newest-first and oldest-first.

## Data / backend
- [S-24] Messages fetched via `email_get_messages` Tauri command, filtered client-side by configured account IDs.
- [S-25] Per-account folder status fetched via `email_get_folder_status` to detect unread/total count changes.
- [S-26] Polls folder status every 30 seconds; reloads full message list only when counts change.
- [S-27] Mark-read invokes `email_mark_message_read` with optimistic UI update.
- [S-28] Delete invokes `email_delete_message` and removes the message from the local list.
- [S-29] Move (Archive / Junk) invokes `email_move_message` and removes the message from the list.
- [S-30] Open invokes `email_open_message` (uses web_link or message id). For an Outlook id it deep-links via `ms-outlook://`; otherwise it opens the web_link. An IMAP message has no web view (empty web_link), so Open is an explicit logged no-op rather than shell-opening an empty string, which would launch Explorer at the install dir (issue #45a).
- [S-31] Reply invokes `email_reply_to_message` with from-email and subject.
- [S-32] Reloads whenever the account filter, folder, message count, or `_refresh` token changes.
- [S-45] Adding a CalDAV/CardDAV account performs RFC 6764 service discovery (`dav_discover_collection`) instead of PROPFINDing only the literal URL typed. A URL that already resolves to a calendar/address-book collection is used **verbatim** (one round-trip, backward-compatible with pre-discovery accounts and exact-collection entries). Otherwise the typed URL — and, as a fallback, the `.well-known/{caldav,carddav}` URL derived from its origin — is walked `current-user-principal` → `{calendar,addressbook}-home-set` → the collections underneath, and the **first** usable collection is stored (for calendars, the first whose `supported-calendar-component-set` includes `VEVENT`, if that property is advertised). This fixes issue #71: a Nextcloud user who pasted the server root got a bare HTTP 401 (the web root rejects a basic-auth PROPFIND) even though other clients — which all discover — connect; the `.well-known` fallback resolves the real DAV context. Discovery uses a **non-redirecting** client and follows any 3xx itself (`dav_propfind`), re-attaching basic auth each hop, so a `.well-known` 301 keeps the PROPFIND method+body (reqwest's auto-redirect would downgrade it to GET) and auth is never dropped across a redirect. All discovery requests target the same host the probe reached (no new SSRF surface vs. the prior single probe). If every candidate 401/403s, the original "Server returned HTTP …, check URL and credentials" message is preserved (a real auth failure is never masked); if the server connects but exposes no collection, a kind-specific "no calendar/address book was found" message asks for the full collection URL. The XML is parsed with small prefix-insensitive scanners (`dav_open_tag`/`dav_inner`/`dav_responses`/`dav_collections`) since servers vary the namespace prefix freely. To pin one specific calendar/address book, the user still enters that collection's exact URL (used verbatim).
- [S-44] CalDAV calendar events are fetched + parsed in this crate (`calendar_get_events` → `fetch_caldav_events` → `parse_ics_events`). A zoned `DTSTART`/`DTEND` (`;TZID=<IANA zone>:<local time>`) is resolved to a true UTC instant and emitted with a `Z` suffix (`caldav_dt_to_iso_tz` via `chrono-tz`): dropping the TZID and emitting the naive wall-clock time made the frontend (which reads naive as UTC) render the event by the zone's offset — 4h early on a GMT-4/EDT account (issue #66). A trailing `Z` is already UTC; a `VALUE=DATE` all-day value is returned verbatim; a floating (zoneless) time keeps the prior naive best-effort; an unknown zone / unparseable / nonexistent local time is logged and falls back to the naive value (never panics).
- [S-46] `email_probe_endpoint` performs an **anonymous reachability check** on a connect preset's endpoint: an IMAPS dial + greeting read (`* OK` / `* PREAUTH`, via `probe_imap_blocking`, proxy-aware through netproxy exactly like `imap_connect`), or an **unauthenticated** `PROPFIND` for DAV. No credentials are sent and nothing is written — these are the handshakes any mail client performs before logging in — so a probe can neither leak a secret nor mutate a mailbox. It is reachability only; `add_*_account` remains the sole authority on whether credentials work. `ProbeTarget` (`{kind:"imap"|"dav"}`) and `ProbeOutcome` (`reachable` / `unreachable` / `not_dav` / `server_error`) are tagged enums on both sides of the IPC boundary, not loose strings. `classify_dav_status` treats **401/403 as reachable** — an unauthenticated PROPFIND against a live collection is *supposed* to be rejected, so scoring it a failure would badge every working preset as broken — while 404/405/410 is `not_dav` (the path moved, which is exactly how a stale preset presents) and 5xx is `server_error` (transient, reported apart from a wrong address). A `DAV:` response header proves reachability whatever the status. Probes use a 10s timeout (not the 30s sync timeout — a pre-flight check must not hang the wizard) and pass through the same `check_host_port` / `check_url` SSRF guard as the add commands, so a preset can never become a route into private address space.
- [S-47] A protocol connection (IMAP / CalDAV / CardDAV) is **two pages**: page one asks *who is your provider?* and nothing else; page two asks for the credentials, with the server settings already filled from that answer. One question per page, and the second is half-answered by the time you reach it. Page one is a three-column grid of **preset tiles** (`src/connect/presets.ts` → `.connect-preset-tile`), each with a brand mark, plus an always-present **"Enter it myself"** tile — presets are a shortcut, never a cage. Picking one fills the server fields and probes the endpoint via [S-46], badging it `ok` / `checking` / `stale` on page two; the badge is **advisory and never blocks Connect** (a probe cannot see credentials, and a restricted network can fail one while a real sign-in succeeds). Page two carries the chosen provider plus a **Change** link, and **Back** returns to page one rather than out of the flow — including for a `?provider=` deep-link, which lands on page one and still has somewhere to go back to.
  - **Icons:** every mark is the icon the provider **publishes for itself** — its favicon, taken from its own site. `scripts/gen-brand-icons.mjs` scrapes each site's `<link rel="icon">` / apple-touch-icon / `/favicon.ico`, sniffs the bytes (a soft-404 serving HTML is never committed as a "mark"), unpacks the one size a 22px plate needs and inlines it as base64 into the generated `src/connect/brandIcons.ts` (`npm run gen:brands`). An icon-set package was the previous source and was replaced: it shipped nothing for Yahoo, Fastmail, Posteo, mailbox.org, AOL or Yandex Mail — several removed at the trademark owner's request — so a third of the catalog fell back to letters, and what it did ship was a redrawn silhouette rather than the mark the provider actually uses. Every preset in the catalog now carries a real mark, pinned by `presets.test.ts`; the brand-coloured monogram survives only as the fallback for a preset added before its brand is generated.
    - **Inlined, not fetched at runtime:** the Connect window has to draw offline, and rendering a settings page must not tell a dozen third parties which providers a user is browsing. `scripts/lib/favicon-image.mjs` turns whatever the site published into one tile-sized PNG — unpacking the ~64px entry out of a multi-size `.ico` (most store theirs as uncompressed bitmaps: microsoft.com ships 17 KB for six copies) and resampling anything oversized (Gmail publishes a single 256px image) — so the whole catalog of 18 marks costs ~23 KB instead of ~170 KB. Only the container changes; the artwork is never redrawn. `brandIcons.test.ts` guards the committed bytes offline (magic bytes match the declared mime, per-mark and total size budgets, `https` provenance), and `brandIcons.network.test.ts` (`npm run test:brands`, opt-in per [S-48]) re-contacts every `source` URL and fails when one stops serving an image. It deliberately does **not** diff bytes: a provider redrawing its own favicon is their business, and the answer is to re-run the generator and review the diff.
    - **One plate for all of them:** favicons are drawn for a browser tab, so they assume a light background — GitHub's is a near-black octocat on transparent, invisible on a dark surface — and they arrive at different paddings, shapes and aspect ratios. Every mark therefore renders inset on the same light plate (`BrandMark`, `--brand-plate` / `--brand-plate-border`), which fixes both problems at once: legible in either theme, and a row of them reads as one set. The same component serves the Connections list, the picker's provider header and the preset tiles.
  - **No Outlook.com preset.** Microsoft sign-in needs no password and never expires, so an IMAP tile beside it would present the worse option as an equal; `presets.test.ts` pins its absence, including its domains. Outlook users take the Microsoft card on the picker.
  - **Field layout:** the IMAP server and its port are one setting split across two boxes, so they share a row (`ConnectField.inline` / `narrow` → `.connect-field-row`) instead of being separated by the username field, which read as three unrelated questions and split the very pair a preset fills. The reachability verdict renders **directly under that row** (`HealthLine`, placed at `serverRowIndex`) rather than floating above the form, so the check sits against the settings it judges.
  - **Address auto-detect:** typing an address on page two selects the matching preset (`matchPresetByEmail`: exact domain or a subdomain of it, never a suffix collision such as `notgmail.com`) — but only while the user has not hand-edited a server field and did not choose "Enter it myself". Both set `serverEdited`, which means "the user owns these fields"; declining the list must not then have the list fill the server field behind their back. Choosing "Enter it myself" also **clears** the server fields to their defaults, so arriving there after picking Gmail never leaves `imap.gmail.com` sitting under a manual label.
  - An app-password preset shows that requirement plus a link to the provider’s page, since an account password rejected by Gmail/Yahoo/iCloud/Fastmail is the single most common cause of "login failed" here. Self-hosted presets (Nextcloud, Baïkal, Synology) carry a `{token}` placeholder and are never probed — their host is whatever the user types; **Connect stays disabled while any token remains**, with a hint naming it. There is deliberately **no "Other" preset**: a catalog entry that fills the form with `{imap-server}` is a worse answer than an empty form, which is what the manual tile gives. Every preset-filled field stays editable.
- [S-48] Preset server settings are verified against reality by `npm run test:presets` (`src/connect/presets.network.test.ts`), which contacts every non-templated endpoint in the catalog the same way [S-46] does and fails when one stops answering. It is **excluded from `npm run check`** by the `**/*.network.test.ts` exclude in `vitest.config.ts` — the default gate stays offline and deterministic — and runs from its own `vitest.presets.config.ts`. The brand marks are checked the same way and for the same reason (`npm run test:brands`, `vitest.brands.config.ts`): both suites snapshot something that lives on somebody else's server. The suite reports which self-hosted presets it skipped, so "all green" never overstates coverage. A failure is data, not a flake: it means a provider changed its settings and the catalog needs updating. (It earned this on its first run, catching two endpoints that no longer resolve.)
- [S-49] The Connect picker lays **services and protocols out in three columns** (`.connect-provider-grid`, stepping to 2 then 1 only below 500/360px — both under the window's 520px minimum, so three columns hold at every draggable size), and each card shows its provider name and a **bullet list of the widgets that connection feeds** (`ConnectProvider.uses` → `.connect-use`), and nothing else. The one-line blurb is **not** rendered: "Outlook, Office 365, Exchange Online" answered a question nobody was asking, while the widget list answers the real one. Same treatment for service and protocol cards — they share one component, so they cannot drift. A protocol card additionally shows a **strip of the brand marks it reaches** (`.connect-provider-brands`, first six then `+N`): "IMAP" means nothing to most people, while the Gmail / iCloud / Fastmail marks underneath say what it is *for* at a glance. Providers with no presets render no strip. The list reuses the `widget.<key>.label` keys, so it reads exactly as the Add-Widget picker and localizes for free. Rendered as spans with a CSS bullet, not `<ul>/<li>`: a button.s content model is phrasing content, so a real list inside it is invalid HTML and makes screen readers announce list semantics from inside a control. The registry's own `providers` field can't source this: only a handful of widgets declare it and none of the protocol ones do. `providerUses.test.ts` source-scans the catalog (providers.tsx carries Solid JSX, so vitest can't import it — same constraint that produced `visibility.ts`) and fails if any key lacks a label, so a renamed widget can never render a raw key. The Connect window is 760×700 (min 520×520), widened from 560 because three columns collapsed to two at the old size. Protocol labels shortened to `IMAP` / `CalDAV` / `CardDAV` / `RSS / Atom` — the parenthetical provider lists no longer fit a third-width card, and the widget list carries the meaning.
- [S-50] The Connect window has **no in-app header**. It is built with `decorations(true)`, so the OS title bar already provides a title and a close button; the former `.connect-head` duplicated both. The step heading (`Add a connection` → `Connect IMAP` → `Connected` …) is pushed to the real title bar via `setTitle`, so the information survives the removal. **Back** is the one control the title bar cannot provide, so it moves inline to the top of the body rather than justifying a second header; it still appears only when a provider was chosen in-window (not deep-linked via `&provider=`) and more than one provider is pickable.
- [S-51] GitHub can be connected by **OAuth device flow** (`email_start_github_device_auth` / `email_poll_github_device_auth`) as well as by personal access token. Device flow is the grant for a desktop app: it needs only a public `client_id`, no client secret, which the app has nowhere safe to keep. The frontend runs **one** device-code path (`beginDevice`), parameterised by `ConnectProvider.device` — Microsoft and GitHub execute the identical grant, so a second copy of the polling loop would just be a second place for the interval or stop-on-error to drift. Both GitHub paths converge on `persist_github_token`, so token verification, account id, and display-name fallbacks exist once; a stored account is `provider: "github"` either way and widgets cannot tell them apart. `authorization_pending` / `slow_down` are polled through as "still waiting" (they are the normal state while the user is on the approval page), while `expired_token` / `access_denied` surface as actionable messages. Polling waits the server's stated `interval` + 1s.
  - **The token card stays** (`github-pat`, "GitHub token"). This is not a duplicate implementation kept behind a flag: GitHub Enterprise Server cannot authenticate against a github.com OAuth app, so a token is the *only* way in for those users, and the token form is the only one carrying the `apiBaseUrl` field. The OAuth path never targets an Enterprise host.
  - **Release gate:** the OAuth card is `devOnly` — hidden from the picker unless developer mode is on. This is a **pre-release gate, not a provisioning marker**: the OAuth app is registered and the flow works. Google sits behind the same flag with a fully provisioned client id, which is the proof that `devOnly` tracks launch readiness rather than credentials. Unhiding either is a release decision, never a side effect of wiring up a client id. The token card stays visible throughout, so GitHub is reachable either way.
  - **Provisioning:** registered as the "Themia" OAuth App (`github.com/settings/applications/3783370`, owner `nwalser`) with **Enable Device Flow** ticked. `GITHUB_CLIENT_ID` is checked into source deliberately — the device flow ships **no client secret** (that is the property that makes it right for a desktop app), and no secret was ever generated for this app, so there is nothing here to leak. Should the id ever be cleared, `github_client_id()` refuses with registration instructions rather than firing a doomed request. Scopes match the token path exactly (`repo read:user notifications`), guarded by `s51_github_device_scope_matches_the_token_path`.
- [S-52] The IMAP preview (`build_imap_preview`, fed by [S-38]'s `BODY.PEEK[TEXT]`) is derived by **walking the message as MIME**, not by scrubbing the raw body. `BODY[TEXT]` of a multipart message is the whole body — the `This is a multi-part message in MIME format.` preamble, every boundary delimiter and every part's own headers — so the previous strip-tags-and-collapse pass previewed `Content-Type: text/plain; charset=utf-8` and ran out of its 200 chars before reaching a word the sender wrote (issue #114). The walk instead takes the top-level `Content-Type` from the fetched header block (which carries the `boundary`), splits the body on its delimiters, recurses into nested multiparts and `message/rfc822`, and **prefers the first `text/plain` leaf, falling back to `text/html`** — the plain part is what the sender wrote for this purpose, the HTML twin the same words in markup. The chosen part is decoded from its `Content-Transfer-Encoding` (`quoted-printable` soft line breaks + `=XX`, `base64`) and its charset (UTF-8, else a Latin-1-family label through the Windows-1252 table, else lossy) **before** the whitespace collapse and the 200-char truncation, so `=20` and `=C3=A9` never reach the user. `Content-Disposition: attachment` parts are skipped even when `text/*`, non-text leaves are ignored, `<script>` / `<style>` blocks are dropped whole from an HTML part and its entities decoded, and a **declared** `text/plain` part is trusted verbatim so a plain-text `<https://link>` is not eaten as a tag (an entity that declares no `Content-Type` still gets the tag strip: omitting the header is what senders of raw HTML do). Work is bounded — 6 levels, 32 parts, 16 KB decoded per part — since a preview needs 200 chars and the fetch thread must not be spinnable by a hostile structure. **A structure that yields no text part previews empty**, never boundary soup: a declared-but-unused boundary, an attachment-only mail and a corrupt base64 part all resolve to `""`, which is the same "absent text part" case [S-38] already specified. Structured headers are read through `parse_header_field_raw` (no RFC 2047 decoding), because a boundary may legally contain `=?`. Only the IMAP path builds a preview locally; Graph and Gmail return a server-side snippet.
- [S-53] Google's Desktop OAuth client secret is **not in the source**. It is read at compile time from `THEMIA_GOOGLE_CLIENT_SECRET` (`option_env!`); `scripts/release-local.ps1` loads it from `.env` and refuses to release without it. Google treats this secret as non-confidential for installed apps, so shipping it in the binary is fine; keeping it out of the public repository stops forks from impersonating the official client and keeps secret scanners quiet. A build without it rejects `start_google_auth` before opening the browser, and token exchange and refresh fail with the same message instead of sending a request Google would refuse.

## Interactions
- [S-33] Single-click sets keyboard focus on a row; double-click opens the message.
- [S-34] Arrow Up/Down move keyboard focus; Home/End jump to first/last; PageUp/PageDown step by 10.
- [S-35] Enter opens the focused message; Delete deletes it (unless it belongs to a Google account); Escape clears focus.
- [S-42] The keyboard-focus highlight resets when the user clicks anywhere outside a message row (the widget's own chrome, another widget) via a global mousedown handler, and when the Themia app loses focus entirely (clicking another app or the desktop) via the shared `onAppBlur` helper (Rust `themia-blur` broadcast + `window blur` fallback). Mirrors the folder / shortcut / contacts / todo widgets.
- [S-36] Keyboard input routed via the Rust low-level hook because widget windows are `WS_EX_NOACTIVATE`; clicking the widget activates its keyboard router.
- [S-37] Row view renders a sticky column header row with the labels for the active columns.
- [S-38] Account list also accepts IMAP accounts (added via the Connections page); IMAP messages share the same merged feed, and fetch / mark-read / delete / move dispatch on provider in the Rust backend. Mark-read / delete / move each resolve the message id's own source folder to a real mailbox name via IMAP SPECIAL-USE attributes (RFC 6154) with name-candidate fallback (so Gmail's `[Gmail]/Sent Mail`, Outlook's `Sent Items`, etc. work without per-provider hacks), `SELECT` it, then act by UID. **UIDVALIDITY guard:** each message id encodes `folder|uid|uidvalidity`; before a mutation, `ensure_uid_validity` compares the id's captured UIDVALIDITY against the freshly-`SELECT`ed mailbox and **refuses** (typed `Err`, no-op) on a mismatch — a recreated mailbox reuses UIDs for different messages, so acting would mark/delete/move the wrong one (silent data loss for delete). The guard fires only when both values are known and differ; a legacy two-part id (`folder|uid`) or a server that omits UIDVALIDITY proceeds unchanged. Fetch pulls the most-recent `messageCount` messages via the sequence-number range `[exists-count+1 .. exists]` (`recent_seq_range`), issuing a **parenthesized** att list `FETCH <range> (RFC822.HEADER FLAGS UID BODY.PEEK[TEXT])` — RFC 3501 only permits a bare att when there is exactly one, and a strict server (Dovecot) rejects the unparenthesized multi-att form with `Error in IMAP command FETCH: Invalid arguments` (issue #45); lenient servers (Gmail/Outlook) accept either, which masked the bug. The `BODY.PEEK[TEXT]` section (PEEK so the fetch never sets `\Seen`) feeds a short plaintext **preview** per message ([S-52]) — IMAP messages previously hardcoded an empty preview (issue #45b). An absent text part yields an empty preview, never an error. IMAP folder status (S-25) uses an IMAP `STATUS (MESSAGES UNSEEN)` call, not the Graph path (IMAP has no OAuth token). rust-imap 2.x returns the STATUS counts as an **unsolicited response**, not in the `Mailbox` that `.status()` returns (that stays zero), so `imap_folder_status_in_session` reads MESSAGES/UNSEEN by draining `session.unsolicited_responses`; reading `mailbox.exists` there previously reported 0/0 for every IMAP folder. A per-account fetch error is **logged** (`email:get_messages`) and, when *every* configured account fails, surfaced as the widget error state (S-06); an empty result means "fetched OK, mailbox empty" and renders "No messages". The two are never conflated. The post-login fetch path (`fetch_imap_messages_from_session`, stream-generic) has automated integration coverage (issue #45): an in-process plaintext mock IMAP server drives the real select/fetch/parse code in plain `cargo test` (no TLS/Docker/network), asserting newest-first ordering, header parsing, and `\Seen`→is_read. The mock enforces the RFC 3501 fetch/status grammar (rejects a bare multi-att list as `Invalid arguments`), so the suite reproduces the strict-server path in-process and guards that the production att lists stay parenthesized. The same mock also drives the stream-generic mutation paths (`imap_set_flag_in_session` / `imap_delete_message_in_session` / `imap_move_message_in_session` / `imap_folder_status_in_session`), which previously had ZERO automated coverage — the blind spot that hid #45: mark-read / delete / UID-MOVE / STATUS all round-trip, STATUS reads the count back as 3, and a UIDVALIDITY mismatch makes delete + mark-read refuse. Regression guards also cover: a failed FETCH surfaces as `Err`, never a silent `Ok(vec![])`, and an empty mailbox (EXISTS=0) is a successful empty fetch. The implicit-TLS handshake itself is not exercised by these tests.
- [S-39] The Source tab's account toggle list is scoped to email-relevant providers (Microsoft / Google / IMAP): only those connections appear as toggles. The "Manage connections" button opens the full Connections page **unfiltered**: every connection is listed and the same **Add connection** button is offered ([S-40 email]) there, identical to reaching it from the sidebar. (Per-widget scoping lives only in the toggle list, never on the Connections page.)
- [S-40] The Connections page does **not** list providers. It offers **Add connection** in two places, both opening the dedicated Connect window (a separate OS window, `index.html?connect=1`) on its provider picker: a button pinned **top-right of the section header** (`.am-add-btn`), and a **ghost row** closing the connection list (`.am-add-ghost` — an `.account-row` with the fill removed: dashed outline, dashed logo well, muted label). The two placements answer the two moments the action is wanted — arriving to add something, and finishing the scan of what is already connected — and the ghost reads as the next empty slot rather than as another connection. The ghost renders only when at least one connection exists; with none, the empty state (`.am-empty`) explains why to connect and the header button is the single affordance. A `&provider=` deep-link still jumps straight to one provider. The window verifies the connection (the backend add/auth call connects before persisting) and shows provider-aware troubleshooting tips on failure. The provider catalog therefore lives in exactly one surface — previously the same picker was duplicated inline in Settings, so every added provider grew the Settings page and the guided flow had a rival that offered no guidance.
- [S-41] On a successful connection the Connect window broadcasts `accounts-changed` (sync.ts BroadcastChannel); the Connections page and any open widget account lists reload live, then the window closes.
