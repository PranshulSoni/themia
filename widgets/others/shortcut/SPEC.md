# Shortcut Spec

Behavior tags are stable IDs. When adding behavior, append a new [S-NN]; never renumber or reuse existing tags. When behavior is removed, delete the bullet but don't reuse its tag.

The Shortcut widget holds a collection of shortcut items. Each item points to a URL, a local file/folder path, a Windows `shell:` namespace path, or an **app layout** (a tree of panes each assigned an app/URL/path that snaps onto the clicked display). Items are opened by double-click (or single-click when `clickMode` is `single`).

## Display
- [S-02] Empty state shows "Drop files or URLs here, or click ⚙ to add." when no items are configured.
- [S-03] For URL items, loads favicon from Google's faviconV2 endpoint (`https://t3.gstatic.com/faviconV2?...&url=<encoded origin>&size=64`) keyed by the URL's full origin (scheme + host), so subdomains resolve their own icon (e.g. `keep.google.com` → Keep's favicon, not the root Google one; the older s2 `?domain=` endpoint collapses subdomains to the root domain). Falls back to a Globe icon if the favicon fails or URL parse fails.
- [S-04] For file/folder items, loads a Windows shell icon via `get_file_icon` (size 48 in grid, 32 in list/details); falls back to a folder icon while/until icon loads.
- [S-05] Per-item display name: custom `label` if set; else URL hostname with `www.` stripped; else filename with extension removed.
- [S-06] Favicon error state is tracked per item and resets whenever the item's URL changes.
- [S-17] Shell paths (`shell:*`) render the REAL Windows namespace icon, the same one Explorer shows: `get_file_icon` resolves them through `SHParseDisplayName` + `SHGetFileInfoW(SHGFI_PIDL)`, since a `shell:` URI has no file-system path. The lucide quick-set glyph is only the placeholder shown while the shell answers (or if it refuses). The Recycle Bin therefore also switches between the full and empty icon on its own; its icon is cached per fill state so the two variants never share a slot.
- [S-18] When `label` is empty for a quick-set shell path, the widget displays the quick-set's friendly label (e.g. "Recycle Bin") rather than the raw `shell:` URI.
- [S-21] Widget stores an ordered array of items in `config.items`; each item has a stable `id`, `path`, and optional `label`.
- [S-22] `viewMode`: `grid` (default) | `list` | `details`. Grid = tiles with icon + name centred; list = icon + name row; details = icon + name + path columns.
- [S-23] `itemSize`: `small` | `medium` | `large` controls tile/row density (list + grid).
- [S-24] `hideHeader` toggles the widget title bar.
- [S-25] Header shows a Link icon + title (`label` override, else "Shortcuts").
- [S-32] Root element gets `drag-over` class while a compatible native drag hovers the widget.

## Configuration
- [S-07] Each item has `path` (URL, local path, or `shell:` URI) and optional `label` overriding the auto-derived display name.
- [S-08] "Add URL" input: typing a URL and pressing Enter or clicking Add appends a URL item; bare strings are prefixed with `https://`.
- [S-09] "Add file…" and "Add folder…" buttons open native pickers (`@tauri-apps/plugin-dialog`, `multiple: true`) and append each selection as a new item.
- [S-10] After folder/file picking, calls `push_windows_to_desktop` to restore desktop z-order.
- [S-11] Items list in config shows icon, display name, full path, and an ✕ button per row to remove. Rows can be reordered by dragging. File/folder AND shell rows load the Windows shell icon via `get_file_icon` (so folders show the real folder icon and This PC / Recycle Bin the platform ones), falling back to a lucide folder / quick-set glyph while/until it loads; URL/layout rows use their lucide/favicon icons.
- [S-16] The Windows locations (Recycle Bin, This PC, Downloads, Documents, Desktop, Pictures, Home, Control Panel, Network) are SWITCHES in the "Add shortcut" window ([S-66]), one line each: real shell icon, name, toggle. Turning one on appends the matching `shell:<name>` item; turning it off removes every item pointing at it again, so the switch always reflects what the widget holds. The raw `shell:` URI is the row tooltip, never body text.
- [S-61] The config sections are ordered Display FIRST, then the shortcuts section LAST. The shortcuts section sits at the very bottom of the page, after the Display options. It has NO "Shortcuts" section header; the only header in it is the inner "Items" header. There are TWO add affordances, both opening the same window ([S-66]): an accent `btn-primary` "+ Add" button on the right of the Items header, and a `btn-add` "+ Add shortcut" button at the END of the list, full width and at the item rows' own height (59px) so the column reads as equal blocks ending in the add gesture. The configured-items list grows with the content; it never scrolls inside a fixed-height box (the `.shortcut-items-list` class pins `max-height: none` to override the shared `.cfg .items-list` rule; only the config surface itself scrolls when the page overflows). With no items configured the list is replaced by an empty-state line, and the end button remains.
- [S-66] Adding a shortcut happens in a DEDICATED window, not inline in the config panel: the add buttons ([S-61]) invoke `open_shortcut_add_window` (singleton labelled `shortcut-add`; re-invoking focuses it and emits `shortcut-add-navigate` to retarget the widget). The window renders NO in-page header — it is built decorated and titled "Add shortcut", so the OS title bar is its header. Its body is one list: Link (its URL field is always open, never behind a disclosure), File (native file picker), Folder (native directory picker), App layout (appends a fresh layout item, opens the layout editor and closes itself), then the Windows locations as switches ([S-16]). It writes through the shared per-view layout store, so the widget and config window update live, and it stays open after an add (a check marks what landed) so several shortcuts can be added in one visit. Escape closes it. Its label MUST be listed in `capabilities/default.json`, or every plugin call it makes (the pickers, the close, the event listener) is denied silently and the buttons do nothing — pinned by `src/capabilities.test.ts`.

## Context menu
- [S-26] Item right-click offers a type-specific menu, always starting with Open (Launch layout for layout items; "Open N" when a multi-selection is right-clicked) and ending with Rename + Remove (destructive). Type-specific middle actions (single selection only): URL → Copy URL; file → Open file location (reveal in Explorer via `open_in_explorer`'s `/select`), Copy path, Change file… (re-pick the target via the native file picker, keeping id + label); shell → Open location, Copy path; layout → Edit layout… (opens the detached layout-editor window via `open_layout_window`). Rename is disabled while multiple items are selected.
- [S-27] Widget chrome right-click offers view-mode switcher (Grid / List / Details), item-size selector, click-mode toggle, and hide-header toggle.

## Data / backend
- [S-12] `open_url` invoked for URL items on activation.
- [S-13] `open_file` invoked for file items on activation, opening the path with the OS's default associated app via `ShellExecuteW` "open" verb (with a context-menu fallback). Directories naturally land in Explorer; files launch their default handler (image viewer, Word, browser, etc.).
- [S-14] `get_file_icon` fetches the icon data URL for local paths; cached per path for the widget's lifetime.
- [S-19] Shell paths open via `open_in_explorer`: the backend routes non-filesystem paths through `ShellExecuteW`, which resolves `shell:` URIs. (Plain folder paths also work here via the `/select,` Explorer verb if needed; shortcut items prefer `open_file` for the in-place "open default" semantics users expect.)

## Interactions
- [S-15] Double-clicking an item opens its target (URL or file/folder/shell path). Single-click opens when `clickMode` is `single`.
- [S-28] Native OLE file drop onto the widget appends a new file item per dropped path. Dropped paths are not copied, only referenced.
- [S-29] `.url` file drops are parsed for `[InternetShortcut]` `URL=` and appended as URL items (falling back to a plain file item if no URL line is found). The item's `label` is set to the `.url` filename (stem), since a custom-protocol target has no good auto-name. The `.url`'s `IconFile=` is captured as the item's `iconPath` for non-http(s) targets (http URLs keep using their favicon).
- [S-30] `.lnk` file drops are resolved via `resolve_shortcut` and appended as a file item pointing at the resolved target (falling back to the `.lnk` path if resolution fails).
- [S-73] Custom URI-protocol targets (`steam://`, `com.epicgames.launcher://`, `file://`, and any `scheme://`) classify as `url` kind, NOT `file`: they open via `open_url` (`ShellExecuteW` "open", which resolves the protocol handler), are never run through broken-target detection (`fs_exists`), and never call `get_file_icon` on the opaque URL. A `url` item with an `iconPath` (e.g. a dropped Steam shortcut's `IconFile`) renders that real icon via `get_file_icon`; it falls back to the favicon, then a Globe glyph, if the icon is missing/fails to load.
- [S-33] `clickMode`: `single` opens items on plain left-click; `double` (default) opens on double-click.

## App-layout items
- [S-50] A `layout`-kind item has the sentinel `path` `layout:` and carries an app-layout tree in `item.layout`. The path column (details view), broken-target detection, and Copy path/URL do not apply to layout items. The display name is `label` (else "App layout").
- [S-72] A layout item's icon previews the apps it opens: an overlapping stack of up to 4 of its assigned panes' icons, in tree order. Each pane icon resolves like a normal shortcut: URL assignments show their favicon (Globe fallback), `lnk`/`path`/`explorer` assignments show their Windows shell icon via `get_file_icon` (Rocket / FileCode / FolderOpen lucide fallback while/until it loads). When the layout has NO assigned panes, it falls back to the generic `LayoutTemplate` lucide glyph.
- [S-51] Activating a layout item (double-click, or single-click when `clickMode` is `single`) walks `item.layout` into launch entries and invokes the `launch_app_layout` Tauri command, which snaps each assigned pane onto the display the click happened on. Failures are logged, not surfaced.
- [S-52] The tree is walked with the screen work-area as the root rectangle (0,0,100,100 in percent) and recursively subdivided per split `direction`/`ratio`. Each *assigned* leaf yields one entry with `{kind, target, label, args, xPct, yPct, wPct, hPct, reuseIfRunning, matchHint}`. A 50/50 vertical split places child `a` at x 0–50 and child `b` at x 50–100, both full height.
- [S-69] Assignment kinds are `lnk` (Start Menu app), `url` (web URL), `path` (custom file/path), and `explorer` (open a folder in File Explorer). `explorer` flows through to the backend as its own launch-entry kind. The backend opens the folder via ShellExecute and snaps the resulting File Explorer window onto the pane, matching it by window CLASS (`CabinetWClass`), never by exe, because `explorer.exe` also owns the desktop (`Progman`) and taskbar, which must never be moved. It snapshots existing `CabinetWClass` windows before launch and positions the new one (falling back to the foreground Explorer window if the folder reused an existing window). `explorer` entries carry no `args`/`matchHint` and `reuseIfRunning: false`.
- [S-53] A layout with no assigned leaves produces no entries; activating it is a no-op (no `launch_app_layout` call).
- [S-70] URL panes are snapped onto their pane like any other entry. Because `ShellExecute` on a URL returns a transient launcher pid (and an already-open browser opens the URL as a tab in an existing window, creating no new window), the backend resolves the default `https` handler's exe basename (`default_browser_exe()` → UserChoice ProgId → `shell\open\command`) and uses it as the match hint. The existing reposition-if-running + wait-for-new-window machinery then locates the browser window and sizes it to the pane, instead of the browser keeping its previous size.

## App-layout configuration
- [S-55] The "Add shortcut" controls offer an "App layout" option. Choosing it appends a fresh layout item (single empty leaf) and opens the detached layout-editor window for it.
- [S-57] In the items list, a layout row shows the assigned-leaf count ("N apps") instead of an editable path, and a pencil button that opens the layout-editor window (no file re-pick button).
- [S-58] Editing a layout opens a dedicated detached OS window via the `open_layout_window` Tauri command (passing `parentLabel`, `widgetId`, `viewId`, `itemId`). It is a singleton labelled `layout`: re-invoking focuses the existing window and emits `layout-navigate` to retarget it. The window reads + writes the item's `layout` tree (and `label`) through the shared per-view layout store, so edits sync live to the widget window and config window.
- [S-59] The editor window shows a name field + close button and the pane canvas. Hovering a pane reveals split-horizontal / split-vertical / remove buttons (remove hidden when the tree is a single leaf); dividers drag to set the split ratio (clamped 0.05–0.95).
- [S-60] Assigning a pane's source happens IN-PANE: there is no side panel and no separate picker window. Each pane carries, centred inside it: the assigned source's icon + name (when assigned), a Source dropdown (App / URL / File / Folder), and the matching target control: a searchable Start Menu app dropdown (App), a URL input (URL), or a path input with a Browse button opening the native picker (File → file picker; Folder → directory picker). Picking an app, or committing a URL/path (blur or Enter), applies the assignment immediately to that pane; an empty target clears it. Switching the Source dropdown clears the current assignment. A small "Clear" button removes the assignment. Shell icons are loaded via `get_file_icon` for app/file/folder targets; URL targets show their favicon.
- [S-68] (Legacy) The detached "assign app" picker window (`open_layout_app_picker_window` / `LayoutPickerWindow`) and its `layout-assign` transient message are no longer used; assignment is in-pane ([S-60]). The command + window remain registered (callable directly) but are unreferenced from the UI; candidates for later removal.

## Default-layout placement
- [S-20] New screens seed one Shortcut widget under the clock at the top-right with two items (Recycle Bin `shell:RecycleBinFolder` and This PC `shell:MyComputerFolder`). Only added when the default grid has ≥3 rows and ≥2 columns.

## URL drops
- [S-34] A native URL drag from a browser address bar (CFSTR_INETURLW, or `http(s)://` CF_UNICODETEXT as a fallback) appends a URL item. Rust forwards the extracted URL(s) in the `urls` field of the emitted `native-drag` event; the widget only consults `urls` when no `filePaths` resolved on the same drop.

## Cross-widget drag / reorder
- [S-35] Items can be dragged between Shortcut widget instances. The source widget starts a native OLE drag (`startDrag({ type: 'widget', widgetJson })`) with JSON payload `{ kind: 'shortcut-item', sourceWidgetId, sourceViewId, dragId, item }`. The RECEIVER owns BOTH halves of the move: it adds the item (fresh item id, preserving path + label) and removes the original from the source widget through that widget's own view store (`sourceViewId` is in the payload because the source may live in another monitor window whose store this window never instantiated). Both writes use `updateWidgetConfig(..., immediate=true)`, bypassing the 50ms save debounce, so a move across monitor windows shows up at once instead of lagging a save tick. A payload without `sourceViewId` is ADD-ONLY: duplicating is recoverable, losing the item is not. The SOURCE never deletes anything: it used to remove the item when `start_native_drag` resolved with `effect === 'move'`, but that promise and the drop event are independent messages into the webview, so the removal could beat the drop handler and an item dropped back into its own list simply vanished. Pinned by `dragOwnership.test.ts` (source-scanned: the losing interleaving needs the real OLE loop, which no test harness can drive).
- [S-37] Dragging an item within the widget view reorders it (in addition to config-list reordering [S-11]). The drag is OLE-driven (the same `get_cursor_state` poll loop that drives cross-widget drag, since a `WS_EX_NOACTIVATE` window suppresses held-button mousemove); on drop the handler resolves the cursor position via `dropTarget` to one of three outcomes: over another row → insert the item BEFORE that row; over empty space (e.g. past the last item) → append at the end; over the dragged row itself → no-op. The same bounding-rect hit-test covers list/details and grid layouts. The item is removed from its old position and spliced into the new slot by id (filter-safe, since DOM order tracks `visibleItems`, a subset of `items()`). A drop that doesn't change the order writes nothing (no undo entry); previously a drop on empty space matched no row and made the item vanish. The sender ALWAYS skips its `effect==='move'` remove path for a self-drop: the receiver registers the `dragId` in `selfHandledDrags` up front, before any early return (source row not found), so a self-drop can never delete the item (regression: registering only after a successful reorder made no-op self-drops vanish). When a live preview ([S-65]) is showing on drop, the handler commits exactly that previewed order instead of re-hit-testing (WYSIWYG); the `dropTarget` splice above is the fallback for drags that emitted no `over` events.
- [S-65] Reorder is shown LIVE during the drag, not only on release. While the OLE drag blocks the JS poll loop, the source widget's `IDropTarget` keeps emitting `DragOver` → `native-drag` `over` events; each one reorders a display-only copy of the visible items (`dragPreview`) so the rows move under the cursor in real time. The dragged row is marked `.drag-src` for the duration. The preview uses the same `dropTarget` hit-test as the commit, so what the user sees is what gets written on drop. The source item id comes from `oleDragId` (set in `startOleDrag`); since real `over` events carry no payload, a self-sourced `shortcut-item` in the event's `widgetData` is also accepted (lets the native bus / tests drive the preview). The preview is committed on a self-drop ([S-37]), reverted to the committed order on `onLeave` (dragging back out), and always torn down when the OLE drag promise settles (drop, cross-widget move, or cancel). If the OLE promise settles after a real drop (`effect !== 'none'`) while a preview is still pending, the source commits that preview itself: the drop event was lost or late, and the preview only ever exists while the cursor is over this widget's own list. `commitPreview` writes nothing when the order is unchanged, so the drop handler having already committed makes this a no-op rather than a second edit.
- [S-38] Drag is initiated by a 5-pixel cursor-move threshold after `mousedown` on an item, mirroring the folder widget's OLE drag pattern. Pointer movement is read via `get_cursor_state` (Win32 `GetCursorPos` / `GetAsyncKeyState`); Chromium suppresses DOM `mousemove` on `WS_EX_NOACTIVATE` widget windows while a button is held, so DOM events alone aren't reliable. Items are NOT marked HTML5 `draggable={true}`; HTML5 drag would race with OLE and trap the gesture inside the widget's own window. The per-item icon `<img>` (favicon / shell file-icon) is explicitly `draggable={false}`, because an `<img>` defaults to draggable, so grabbing a URL item by its favicon would otherwise start a native image drag alongside OLE and, on drop, the favicon's `https://` src would be captured as a URL drop and appended as a spurious new URL item. Disabling image drag leaves OLE as the sole reorder gesture.
- [S-74] The press → click | rubber-band | OLE-drag gesture is driven by the SHARED folder gesture state machine (`widgets/office/folder/gesture.ts`): one `GestureState` replaces the widget's former ad-hoc `pending` / `mousePolling` / `bandOrigin` flags. Every press arms exactly one candidate through `beginPress`, which fully wipes all prior state (candidate + suppress flags) BEFORE arming, so a press can never inherit a stale drag origin. Every exit path resets the in-flight candidate via `resetGestureCandidates` — the poll-loop release branch, the poll-loop error/catch branch, an external item-row `mouseup` ([S-63]), and unmount. A monotonic `generation` token, captured by each poll loop at start, makes a stale loop self-terminate on its next check instead of racing a fresh one (no double-loop). Guarantee: an aborted poll (transient `get_cursor_state` failure) or an external mouseup can NEVER strand a drag candidate that misclassifies the next left press as a drag — which would hand off to OLE, swallow the `mouseup`, and silently kill single-click open until restart (#58). Right-click Open is unaffected (never depends on `click`).

## Undo (Ctrl+Z)
- [S-36] Every user-initiated config mutation (add via drop, remove via ctx menu, rename, reorder, cross-widget receive, sender-side remove on move) records a `widget-config` op-log entry with `widgetId` + label + a full previousConfig snapshot. `undoLast()` reverts by calling `updateWidgetConfig(widgetId, previousConfig)`.

## Selection and keyboard
- [S-40] Plain click selects a single item; Ctrl-click toggles membership; Shift-click selects an inclusive range from the anchor. Selected items carry a `selected` class; selection persists across reorders, and entries are pruned automatically when their items are removed.
- [S-41] Delete removes every selected item as a single `widget-config` op so one Ctrl+Z restores the whole batch. Context-menu `Remove N` performs the same action. Right-clicking an unselected item resets the selection to that item first so bulk actions follow the visible cursor.
- [S-42] Ctrl+A selects every currently-visible item (respects the active search filter). Escape closes the search input if open, otherwise clears the selection.
- Arrow keys move selection along the visible item list (`Shift+Arrow` extends the range). Enter opens every selected item via the same `open_url` / `open_in_explorer` routing used by double-click.
- [S-63] Dragging from the list background (not on an item) draws a rubber-band (marquee): items whose bounding rect intersects the band become the selection live as it grows; a `.rubber-band` overlay renders the rectangle (`--primary-subtle-bg` fill + `--primary-subtle-border`), matching the folder widget. A background press that never crosses the 5px threshold is a plain click and clears the selection. Like the folder widget the band is driven by the `get_cursor_state` GetCursorPos poll loop (WS_EX_NOACTIVATE windows suppress held-button mousemove), so it is inert in non-Tauri/dev contexts. The band is torn down on EVERY release path via a shared `endBand` helper: the poll-loop release branch, the poll-loop error/catch branch, AND a DOM `mouseup` on an item row. The last case matters: a marquee released with the cursor over an item fires the item's `onMouseUp`, which stops the poll loop before its own release branch runs; without clearing the band there the lasso rectangle stayed stuck on screen.
- Keyboard is routed via the `folder-key` Tauri event fed by the Rust WH_KEYBOARD_LL hook (mirrors the folder widget); any mousedown inside the widget calls `activate_widget_keyboard` to claim the hook. A `document` keydown fallback is also installed for non-Tauri contexts (dev/vite) and unit tests.
- [S-62] The widget claims the global keyboard router ONLY on real interaction (root mousedown or an item click), never on mount. The WH_KEYBOARD_LL hook is process-global, so claiming it before the user touches the widget would swallow stray global keystrokes (an Arrow selecting the first item, a later Enter opening it) and leave an item permanently "preselected". An untouched widget therefore never reacts to global keys. The selection is kept only when the click lands on one of this instance's own item rows; clicking anywhere else clears it: the empty list background, this widget's chrome, another widget, or the desktop, mirroring the folder widget where a background click deselects. Mousedowns inside a context menu are ignored so a menu action can still read the selection.
- [S-64] Clicking outside the Themia app clears the selection. A click outside the widget windows lands no DOM mousedown in the webview, so the in-app outside-click handler can't catch it. The reliable signal is the Rust `WH_MOUSE_LL` mouse hook: it fires on every physical click regardless of which window holds the foreground, and broadcasts a `themia-blur` event whenever the click lands outside all themia windows, and the widget clears its selection on it. The foreground hook also broadcasts `themia-blur` to cover keyboard-driven focus changes (Alt+Tab, Win+D) that have no mouse click. A DOM `window blur` listener is installed only as a dev/non-Tauri fallback, since our `WS_EX_NOACTIVATE` window doesn't cleanly re-acquire focus after the first switch, so blur alone clears only the first time. Mirrored by the folder ([S-61]) and contacts ([S-38]) widgets.

## Search
- [S-43] Header search button (🔎) toggles an inline input in place of the title. Input narrows the rendered list to items whose display name or path contains the query (case-insensitive, substring). Escape (in the input or globally) closes the search and clears the query. When `hideHeader` is on, the search button is also hidden; use the context menu to surface it if desired.

## Recycle Bin state
- [S-75] An item pointing at `shell:RecycleBinFolder` shows a count badge on the top-right of its icon while the Recycle Bin holds anything, and no badge while it's empty or the state is unknown (issue #94). The badge shows how many files are in the bin, capped at "99+"; its height and font scale with the item's icon size (42%, clamped 12–20px). The state comes from the `recycle_bin_status` command (`SHQueryRecycleBin` over all drives, `{ items, bytes }`), refreshed once when the widget mounts / gains a bin item and then every 15s via `createPolling` (so it pauses on hibernate). Only widgets that pin the bin poll at all; the status is a process-wide signal with single-flight + 5s age throttle, so N such widgets still cost one IPC per tick. A failed query leaves the previous value in place and never fabricates "empty". The item's tooltip reads "<name> — N items (size)", or "<name> — empty" when the bin is empty.

## Broken-target detection
- [S-44] For file-kind items the widget invokes `fs_exists(path)` and dims the row with a `broken` class when the path doesn't exist. The display name gets a strike-through and the tooltip appends "(target missing)". URL and shell items are never marked broken (hostname / shell reachability isn't checked).

## Display options (parity with folder widget)
- [S-45] Config modal exposes a Display tab alongside the existing Shortcuts (source) tab. Display tab exposes: View (Grid / List / Details), Item size (separate Grid vs List/Details controls), Stretch height (grid only), Open on (Single / Double), Show file extension. Each control writes the corresponding config key via `onChange`. (The header title override AND show/hide-header toggle both live in the shared config Header field, not the Display tab.)
- [S-46] `gridItemSize`: `small` | `medium` (default) | `large`. Drives the grid `minmax()` track width and icon size. Only consulted when `viewMode === 'grid'`. List/details modes still use `itemSize`.
- [S-47] `gridStretchHeight`: when true and `viewMode === 'grid'`, tiles stretch to fill the widget's vertical space (`grid-auto-rows: 1fr`, `.shortcut-item { height: 100% }`).
- [S-48] `showFileExtension`: when true, file-kind items render their basename WITH the extension suffix; URL and shell items are unaffected. Custom `label` overrides still win.
- [S-49] Widget chrome ctx menu shows a Grid-size submenu (Small/Medium/Large + Stretch height toggle) when `viewMode === 'grid'`, falling back to the regular Item-size submenu otherwise. A Show/Hide file extensions toggle sits alongside the existing Show/Hide header toggle.
- [S-71] `gridIconOnly`: when true AND `viewMode === 'grid'`, item name labels are hidden so tiles show only their icon (root gets a `grid-icon-only` class that sets `.shortcut-name { display: none }` and centres the icon within the tile via `justify-content: center`, so it stays centred when tiles stretch to fill height). Consulted only in grid view; list/details always show names. The rename input is still shown when an item is being renamed. The Display tab exposes an "Icon only" toggle (grid view only), and the grid-size section of the widget chrome ctx menu offers a Show labels / Icon only toggle.
